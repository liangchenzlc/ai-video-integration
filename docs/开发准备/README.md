日期：2026-09-15。状态：**开发准备资料已完成，可以开始 T01-A 工程开发**；不表示应用功能、模型效果或发布验收已完成。

本轮用户授权提前完成分模块需求、接口、数据模型及验证示例。因此调整原来“到模块启动时才写详细设计”的资料安排；实际实现仍按 T01–T14 逐模块交付，首版范围和质量门槛不变。

## 1. 开工判定

“可以开始开发”指开发者有明确的范围、契约、数据约束、测试输入和失败预期，可以开展 T01 工程并按依赖进入业务模块。它不要求先取得正式成片、生产模型账户或完成发布评审。真实模型接入、界面定稿与发布分别有自己的门槛，不得混为一个总开关。

| 关口 | 开始条件 | 不可替代的后续证据 |
| --- | --- | --- |
| T01-A/B/C 工程实施 | T01 设计、候选版本、启动契约明确 | 实际安装、lockfile、Windows Job、打包和故障验证 |
| T01-D 界面定稿 | G00 原型、正常/修改/恢复任务与内部走查 | 相关使用者走查；内部自动测试不冒充用户理解 |
| T02–T12 模块实现 | 前置模块通过、本模块需求/API/模型/示例可用 | 应用测试、真实服务准入及媒体效果证据 |
| 云端收费研究 | 对象、输入、型号、次数、上限及费用范围明确且获授权 | 每次实际调用、全部结果与账单依据 |
| T13 分发 | 可用应用、兼容环境、许可和安装策略明确 | 干净机器、签名和升级回退测试 |
| T14 首版发布 | 原 05 的完整门槛不变 | 六条独立样片、两名独立评审、五名新手及配对成本 |

## 3. 资料状态与维护

需求与工程完成状态分开：模块文档标“设计基线”，原 05 复选框只在应用真实验收后勾选。设计契约使用版本 0.1.0；实现发现冲突时同步负责模块、共用契约、示例和验证。
