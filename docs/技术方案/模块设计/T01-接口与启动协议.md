# T01 接口与启动协议

协议版本：1，文档版本：0.3，2026-09-15。本文是 [T01](./T01-桌面启动安全和导航.md) 的规范性附录。字段名、状态、时限和错误处理按本文实施；示例 ID 和令牌只用于测试，不得用于生产。

## 1. 契约来源与通用约定

- HTTP 结构见 [OpenAPI 契约](../契约/t01-http.openapi.json)，合法响应见 [HTTP 示例](../契约/t01-http.examples.json)。
- 管道单帧结构见 [控制消息 Schema](../契约/t01-control.schema.json)，四个方向的完整合法消息序列见 [控制消息示例](../契约/t01-control.examples.json)。本节及后文补充分帧、顺序和跨字段约束。
- 本轮这些文件是设计输入。实现时由 FastAPI 导出 `contracts/openapi.json`，与设计契约核对结构后生成前端类型；不允许出现两套不同的在用规则。
- JSON 字段使用 camelCase；Python 内部 snake_case 通过 Pydantic 显式 alias 转换。拒绝额外字段、重复 JSON 键、NaN/Infinity 和隐式字符串转数字。所有时间长度使用整数毫秒。整数字段按 JSON Schema 的数学整值规则判断：1.0 可归一化为 1，布尔值、数字字符串和 1.5 拒绝；Python 的前置校验与 TS 使用同一规则，不直接依赖两端不同的默认强制转换。
- UUID 使用小写 UUIDv4。`runtimeId` 每次服务启动新建；`generation` 为 Electron 本次应用生命周期内递增整数，从 1 开始。`requestId` 每次请求独立生成，不承担业务防重。
- 控制协议和 HTTP API 主版本均为 1；首个应用与后端构建版本均为 `0.1.0`。同一目录包两者构建版本须完全一致，开发模式也使用这一规则。

## 2. HTTP 请求与响应

Electron main 使用 Node HTTP 客户端访问实际绑定的 `http://127.0.0.1:{port}`，不经过系统代理，不跟随重定向，不发送 Origin/Cookie。地址只能来自当前监督进程握手；renderer 不接收地址和会话令牌。

| 项目 | T01 规则 |
| --- | --- |
| 认证 | `Authorization: Bearer <token>`；token 是 32 个随机字节的无 padding Base64URL，长度 43 |
| Host | 必须且只能为 `127.0.0.1:{实际端口}`；拒绝重复 Host、localhost、其他 IP、用户信息和端口偏差 |
| Origin | 请求出现 Origin 头即拒绝，包括 `null`；不开放 CORS |
| 请求 ID | main 发送 `X-Request-Id`；缺省时后端生成，非法值返回 422 并为错误重新生成 ID |
| 请求体与查询 | 两个 GET 均不接受请求体和查询参数；非空 body 为 400，未知 query 为 422 |
| 响应 | UTF-8 `application/json`，`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`；`X-Request-Id` 与正文一致 |
| 限制 | 认证头不超过 128 字节；T01 请求体硬上限 64 KiB，响应读取上限 64 KiB；超过直接中断，不记录原始内容 |
| HTTP 文档 | 生产禁用 `/docs`、`/redoc`、`/openapi.json`；构建直接导出契约，不经未认证 HTTP 暴露 |

正常响应统一 `{requestId, data}`，失败统一 `{requestId, error}`。`error` 必须包含 `code`、中文 `message`、`affectedIds` 和 `recoverableAction`；T01 无项目对象，`affectedIds` 固定空数组。

认证与来源检查覆盖未知路由和错误处理路径。处理顺序为头部结构/Host → Origin → Bearer → 请求 ID/参数 → 路由与就绪状态；不能由未授权请求探测运行版本。Bearer 通过恒定时间比较，错误响应、异常日志和校验报告均不回显输入认证值。

### 2.1 GET /api/v1/health

成功 `data` 字段：

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| status | 固定 `ready` | 应用已初始化且 HTTP 可处理运行时请求 |
| runtimeId | UUIDv4 | 与当前控制管道和实例一致 |
| generation | 1 至 2147483647 的整数 | 与 Electron 当前代际一致 |
| apiVersion / controlVersion | 均为整数 1 | 协议兼容检查 |
| backendVersion | 三段数字版本 | 与本包前端构建版本一致 |
| uptimeMs | 0 至 JS 安全整数上限 | 从该 API 进程启动起的单调时钟耗时 |

尚未就绪或正在停止时返回 503 `BACKEND_NOT_READY`，不把 `status: starting` 塞进成功响应。管道 `ready` 只表示可以开始 HTTP 验证；main 完成认证健康请求并检查全部版本/实例字段后才进入界面 `ready`。

### 2.2 GET /api/v1/capabilities

成功 `data` 为 `{runtimeId, generation, capabilities}`。数组固定按以下顺序包含 12 项且 ID 不重复：`runtime`、`projects`、`credentials`、`story`、`visualAssets`、`storyboard`、`video`、`audio`、`timeline`、`checks`、`exports`、`costs`。

每项包含 `id`、`enabled`、`reasonCode`。T01 仅 `runtime` 为 `true/AVAILABLE`，其他均为 `false/NOT_IMPLEMENTED`。前端用 reasonCode 映射中文，不根据页面或按钮存在推断后端已实现。

### 2.3 HTTP 错误表

| HTTP | code | recoverableAction | 处理 |
| --- | --- | --- | --- |
| 400 | REQUEST_INVALID | none | 非空 GET body 或非法请求结构 |
| 401 | AUTH_REQUIRED / AUTH_INVALID | restart_backend | 缺少或错误令牌；健康观察遇到即断开，不反复尝试旧令牌 |
| 403 | HOST_REJECTED / ORIGIN_REJECTED | none | 拒绝来源；合法 main 遇到应视作实现错误 |
| 404 | NOT_FOUND | none | 未定义路由 |
| 405 | METHOD_NOT_ALLOWED | none | 已知路由不支持该方法 |
| 422 | REQUEST_INVALID | none | 非法请求 ID 或未知查询参数 |
| 500 | INTERNAL_ERROR | restart_backend | 仅返回固定中文说明，不回传 Python 栈 |
| 503 | BACKEND_NOT_READY | retry_connection | 按启动或健康观察时限处理 |

过大或无法解析的 HTTP 报文可在服务器解析层直接拒绝，不保证返回应用 JSON；main 将其归为 `PROTOCOL_INVALID`。正常应用层 4xx/5xx 必须采用统一结构，FastAPI 默认 422 响应需显式规范化。

## 3. renderer 与 main 契约

仅暴露下列方法，不提供通用 HTTP/IPC 代理。`BridgeResult<T>` 为 `{ok:true, data:T}` 或 `{ok:false, error:{code,message,recoverableAction}}`，不返回原始异常对象。

```typescript
type RuntimeStatus = 'stopped' | 'starting' | 'ready' | 'disconnected'
  | 'stopping' | 'failed' | 'incompatible';
type RecoveryAction = 'none' | 'retry_connection' | 'restart_backend'
  | 'repair_installation';
interface RuntimeSnapshot {
  state: RuntimeStatus;
  runtimeId: string | null;
  generation: number;
  revision: number;
  frontendVersion: string;
  backendVersion: string | null;
  errorCode: string | null;
  recoverableAction: RecoveryAction;
  canRestart: boolean;
}
```

`generation=0/runtimeId=null` 只用于第一次启动前；`revision` 从 0 开始，每次可见状态提交递增，晚到的旧 revision 不覆盖新界面。`backendVersion` 只有验证过当前实例后才赋值。canRestart 仅在 ready、disconnected 和清理已确认的 failed 为 true；STOP_TIMEOUT、starting、stopping、stopped、incompatible 均为 false。成功状态 errorCode=null；版本不符的 recoverableAction 为 repair_installation，停止清理不明为 none，普通失败/断开为 restart_backend，其余为 none。

| 方法 | 精确输入 | 输出 |
| --- | --- | --- |
| getRuntimeState | 无 | Promise 的 `BridgeResult<RuntimeSnapshot>` |
| getCapabilities | 无 | `BridgeResult<CapabilitiesData>`；数据结构来自 OpenAPI |
| restartBackend | `{expectedGeneration: 非负整数}` | `BridgeResult<RuntimeSnapshot>`；返回已受理后的状态，不冒称已就绪 |
| openHelpLink | `{helpId: 'runtime-help'}` | `BridgeResult<{opened:true}>` |
| onRuntimeStateChanged | `(snapshot: RuntimeSnapshot) => void` | 无参数取消订阅函数 |

T01 的 `runtime-help` 固定映射至 `https://fastapi.tiangolo.com/`，只在用户明确点击“后端框架资料”时交系统浏览器，不假称本产品客服或故障修复网站。窗口内的常见错误说明使用本地中文内容。

main 的本地错误码包括 `BACKEND_UNAVAILABLE`、`SPAWN_FAILED`、`START_TIMEOUT`、`STOP_TIMEOUT`、`PROTOCOL_INVALID`、`VERSION_MISMATCH`、`STALE_RUNTIME`、`RUNTIME_BUSY`、`SOURCE_REJECTED`、`REQUEST_INVALID`。这些是桌面错误，不伪造 HTTP 状态。

每个命令校验 sender、主 frame、精确来源和 schema。preload 只转发解析后的参数/快照，不把 Electron event 对象交给回调。订阅后立即查询一次快照，按 revision 合并，解决“先查询后订阅”漏掉变化的问题。

## 4. 双层控制管道

进程结构为 `Electron main → Python supervisor → FastAPI API → FFmpeg`。supervisor 与 API 使用同一 Python 发行目录/可执行文件，通过固定 `--role=supervisor`、`--role=api` 区分。监督进程没有 HTTP 接口、业务数据库或模型任务。

两段管道分别建立独立的发送序列与接收序列：main ↔ supervisor、supervisor ↔ API。监督进程转发时重新编号；不把子进程序号直接当作父通道序号。

### 4.1 分帧与限制

- 每帧是单行 UTF-8 JSON 加一个 LF，禁止 BOM、CRLF、原始多行、空行和重复字段。字符串换行必须 JSON 转义。
- 帧长包含 LF 最大 16 KiB；读取按字节缓存到 LF 后再解码，允许任意拆包和多帧合包。超过上限、非法 UTF-8 或 EOF 留有半帧均视为协议错误。
- 单方向 `seq` 从 1 开始且严格递增 1；跳号、重复或当前管道 runtimeId/generation 不符立即终止当前实例。旧实例管道回调按对象身份直接忽略，不能因此停止新实例。
- 写入由单一串行出口处理背压；待写数据总量不得超过 64 KiB。管道卡住超过 2 秒作为协议失败，不能无限排队。
- stdout 只允许控制帧；stderr 只允许有界、脱敏后的文本日志。禁止原样输出请求、init 帧、环境变量或任意异常局部变量。

每帧必有 `protocolVersion`、`runtimeId`、`generation`、`seq`、`type`、`payload`，结构见 JSON Schema。接收端从专用父管道的第一个合法 init 建立实例上下文，后续消息必须一致；main 对所有返回消息核对自己保存的 spawn 上下文。初始化完成前不开放 API。

### 4.2 消息方向与语义

| type | main → supervisor | supervisor → API | API → supervisor | supervisor → main |
| --- | --- | --- | --- | --- |
| init | 第 1 帧，含一次性会话 token、配置目录、mode 和版本 | 第 1 帧，已核对的同一配置 | 不允许 | 不允许 |
| booted | 不允许 | 不允许 | 不允许 | 已把 API 放入 Job 并恢复其主线程，含 supervisorPid/apiPid |
| ready | 不允许 | 不允许 | HTTP 已绑定且可进行健康验证 | 核对后转发，含回环 host、port、apiPid 和版本 |
| stop | 退出或重启，含原因 | 传递停止原因 | 不允许 | 不允许 |
| stop_ack | 不允许 | 不允许 | 已禁止新工作并开始关闭 | 确认收到 main 的 stop；forSeq 指 main 请求序号 |
| stopped | 不允许 | 不允许 | 不允许 | Job 活动进程已为 0；不是仅收到停止请求 |
| error | 不允许 | 不允许 | 固定错误码/安全说明 | 固定错误码/安全说明 |

监督进程接到 stop 即发送 stop_ack，不等待 API 的确认；API 的确认只用于监督进程诊断，不冒充已经退出。API 正常停止直接退出，不发送含 `activeJobProcesses:0` 的 stopped，因为它自己仍可能处于 Job 中。

supervisor 收到合法 init 后才创建 API。API 必须在初始化后绑定实际 socket，传给 Uvicorn 继续使用，不释放重绑。supervisor 持有创建时返回的真实进程句柄，核对 ready 的 apiPid；main 最后用 HTTP 核对 runtimeId、generation 和构建版本。

`init.tokenB64Url` 解码后必须恰好为 32 字节。示例令牌如 `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA` 仅用于测试；代码不得设默认生产令牌。应用数据目录必须是绝对路径，并与 main 计算的当前用户应用目录一致。

## 5. Windows 监督进程与句柄归属

选择 **Python supervisor + pywin32**。supervisor 持有唯一长寿命、不可继承的 Job Object 句柄；自身不加入这个 Job。Electron 不直接操作 Windows Job 句柄，也不增加用于此目的的原生 Node 模块。

创建 API 的固定顺序：

1. supervisor 创建无名称 Job，设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；不允许 breakaway。
2. 创建 API 专用 stdin/stdout/stderr 管道。只把这三个子端设置为可继承；main ↔ supervisor 的管道、父端、Job/进程句柄均不可继承。
3. 单一创建锁内用 Windows CreateProcess 创建 API，设置 `CREATE_SUSPENDED | CREATE_NO_WINDOW`，保存返回的 process/thread 句柄。T01-A 实现采用 CPython `_winapi.CreateProcess` 包装器，以 STARTUPINFOEX `handle_list` 明确限制三个可继承标准流；pywin32 负责 Job 管理。固定 exe 和 role 通过正确 Windows 参数引用构造，不拼 shell。开发解释器需绕过 venv 重定向启动器，规则见工程实施文档。
4. 先 `AssignProcessToJobObject`，成功后 `ResumeThread`，随即关闭不再需要的主线程及子管道端句柄。失败时终止仍挂起的所属进程并关闭全部句柄。
5. supervisor 经管道发送 init，API 初始化后建立回环 socket；以后 API 创建的 FFmpeg 子进程默认进入同一 Job，禁止 breakaway 标志和把 Job 句柄传给子进程。
6. supervisor 通过真实进程句柄观察 API 退出，通过 Job 查询活动进程数；不用历史 PID 或进程名作为终止目标。

API 另持有按当前 Windows 用户 SID 命名的 `Local\AIVideoIntegration.Api.<SID>` 互斥体，零等待获取（这里展示的是运行时名称，代码字符串按语言规则转义）。占用时返回 `BACKEND_ALREADY_RUNNING` 并退出，不杀掉占用者。其取得/释放在 API 主线程，进程崩溃后的 abandoned 状态允许新实例取得。项目写锁仍由 T02 独立实现。

异常处理：

- main 死亡导致专用 stdin EOF：supervisor 的独立管道观察线程通知关闭，立即终止 Job；即使 API 不响应也不等待云端结束。
- supervisor 崩溃或被终止：最后 Job 句柄由系统关闭，API/FFmpeg 随 Job 清理；main 观察到子进程退出。
- API 崩溃：supervisor 终止仍在 Job 的媒体进程，核对活动数，再退出并报告 API_EXITED。
- supervisor 正常退出：先让 API 在 5 秒内收尾，超时执行 TerminateJobObject，再最多等待 2 秒清理；完成后报告 stopped 并退出。
- Job 设置/归属失败或进程清理无法确认：明确失败，不退化为无管理启动，也不启动下一代服务。

main 对整个停止操作设置 8 秒最终截止。supervisor 卡住时，main 只终止自己持有的该 ChildProcess，系统关闭其 Job 句柄；若未取得可信的清理完成结果，状态为 STOP_TIMEOUT 且禁止直接重启。关闭应用仍可结束 main，后续重新启动应用必须重新获取 API mutex。没有成功 spawn，或上下文已经明确清理完成时，stop 可直接完成，不等待不存在的 stopped 消息。

此机制依赖 Windows API、管道 EOF 和进程调度；T01-A 必须用真实进程验证正常退出与三种崩溃，不以文本设计或 mock 声称通过。

## 6. 生命周期状态与竞争处理

main 用一个监督器拥有状态、spawn 上下文、计时器和重启操作；所有改变进入串行事件处理函数。任何异步回调都同时核对 child 对象、runtimeId 和 generation。

| 当前状态 | 事件 | 下一状态/处理 |
| --- | --- | --- |
| stopped | 首次启动 | generation+1、新 runtimeId/令牌，进入 starting |
| starting | 管道及 HTTP 全部验证成功 | ready，记录当前后端版本 |
| starting | 30 秒总截止、spawn/协议/子进程错误 | 清理所属进程后 failed |
| starting | API/控制/构建版本不符 | 清理后 incompatible，要求修复安装 |
| ready | 子进程退出/管道断开/认证失效 | disconnected，立即禁用业务 |
| ready | 连续 3 次健康超时/503/网络失败 | disconnected；前两次不触发重启 |
| disconnected | 同一存活实例健康恢复 | 核对全部身份后 ready；不自动提交业务 |
| ready / disconnected / failed | 明确 restartBackend | stopping → stopped → 新 starting |
| starting / stopping | 同一重启的重复点击 | 合并到同一操作；不新增进程 |
| 任意非 stopped 状态 | 关闭应用 | stopping；关闭意图优先，禁止后续重新启动 |
| stopping | 收到 stopped 且 supervisor 退出 | stopped；仅显式重启且未关闭应用时创建下一代 |
| stopping | 无法确认清理完成 | failed/STOP_TIMEOUT，禁止自动启动下一代 |
| incompatible | 修复安装后重新启动应用 | 重新走完整启动协议 |

重启请求带 `expectedGeneration`。当前操作正在处理旧 generation 的重启时，相同请求合并；重启已完成后旧 generation 的点击返回 STALE_RUNTIME，不能再次重启新实例。不同请求在已有生命周期操作期间返回 RUNTIME_BUSY。

界面关闭后收到 ready、stop_ack、成功 HTTP 或旧进程退出事件都不能取消关闭意图。停止后清除令牌、地址、计时器、挂起 HTTP 与事件订阅；子进程未清理完不能把状态先写成 stopped。

| 参数 | 固定初值 |
| --- | --- |
| 完整启动截止 | 30 秒，从 spawn 前开始，用单调时钟 |
| init 接收截止 | 子进程启动后 5 秒，且受完整启动截止约束 |
| 单次健康 HTTP 超时 | 1500 毫秒 |
| 启动 HTTP 验证间隔 | 上次请求结束后 500 毫秒，最多到启动截止 |
| 稳态健康间隔 | 每 5 秒，禁止重叠请求 |
| disconnected 存活实例重查 | 每 5 秒，身份变化立刻失败；进程已死时只等用户动作 |
| 正常停止宽限 / 强制清理观察 | 5 秒 / 2 秒 |
| main 整体停止最终截止 | 8 秒；失败时只终止所属监督进程并记录无法确认清理 |

这些是实现常量，测试使用可注入时钟和固定延迟；实机测量后如需修改，应同时更新本文和对应测试。

## 7. 脱敏与协议测试样例

日志只允许 runtimeId、generation、requestId、PID、状态、错误码与耗时。令牌内容及其前后缀、Authorization、init 原文均不得写入日志、诊断或测试快照；只记录 `authenticated: true/false` 等状态。

必须覆盖：逐字节拆帧、多帧合包、UTF-8 字符跨包、16 KiB 边界、半帧 EOF、错误序号、旧代际消息、版本不符、ready 后立刻退出、启动中关闭、双击重启、健康响应晚到、错误令牌和日志秘密哨兵。Schema 校验通过后仍需验证消息方向、跨字段约束与状态条件。
